本文适合已经能导入配置、连接成功并会查看基本日志的用户。目标不是堆叠复杂字段，而是让一条请求为什么走直连、某个节点或自动选择组变得可解释、可验证、可回退。还没完成首次导入与 VPN 授权，请先看 [sing-box 使用教程](/posts/22-sing-box-next-gen-proxy-tutorial)。

**前置条件：** 这篇是 [sing-box 使用教程](/posts/22-sing-box-next-gen-proxy-tutorial) 的进阶篇。必须先在基础篇确认订阅可导入、VPN 权限已授予、单个节点能连接并会查看日志；否则不要直接修改多出站或 TUN。

## 一、开始前：把“规则、出站、TUN”分开理解

- **规则**回答“这条请求应该交给谁”。它可按域名、IP、网络类型或应用等条件匹配，再指定动作或出站。
- **出站**回答“交给谁以后如何出去”。常见类型包括直连、单个节点、手动选择器（selector）和自动测速组（urltest）。
- **TUN**回答“客户端怎样接到系统流量”。它是虚拟网络入口，不会替你决定规则优先级，也不会自动修复无效节点。

修改时一次只处理其中一层。例如，目标网站只在规则模式失败，先查看规则命中，不要同时更换节点、改 DNS、启用 TUN。先保存一份当前可用配置；每次修改都保留可回退版本。

## 二、自定义规则：从一个明确目标开始

规则应当服务于一个可测试的需求，例如“某个工作域名固定走工作策略组”或“局域网地址保持直连”。不要以模糊的“所有国外网站”开始，也不要用大量正则表达式替代已有规则集。

推荐顺序：

1. 写下目标域名、预期出站与测试页面。
2. 在现有规则中查找是否已有命中；重复规则会让判断变难。
3. 新规则使用稳定的域名后缀、完整域名或官方规则集条件，并明确指定目标出站标签。
4. 把更具体的规则放在通用规则之前；保存后只访问该目标一次。
5. 在日志中确认命中的规则与最终出站标签，再决定是否保留。

如果日志显示 `unknown outbound`，通常表示规则引用的出站标签不存在或拼写不一致；先核对标签，而不是更改节点地址。如果出现 `unknown field` 或配置校验错误，说明字段与当前内核版本不兼容；记录字段路径和版本号，让配置来源给出兼容写法。有关规则条件和动作的完整定义，以 [sing-box 官方 Route Rule 文档](https://sing-box.sagernet.org/configuration/route/rule/) 为准。

## 三、多出站：手动选择与自动测速各负责什么

多出站不是把多个节点随意放进同一处。先为每个可连接节点设置稳定、可读的标签，再建立两类上层策略：

- **selector**：由你手动指定当前节点。适用于需要固定出口、复现问题或比较两个节点。
- **urltest**：按照设定 URL 周期测试候选出站，自动选择结果较好的成员。它适合日常备选，不等同于带宽、流媒体可用性或账户风控检测。

配置前确定一个唯一的“默认策略组”，让规则统一引用它；需要例外时才指向另一个策略组。测试自动选择时，固定测试 URL 和时间段，先确认各成员本身能连接，再观察自动组的选择结果。`urltest` 的候选出站、测试 URL、间隔和容差都有独立含义，详见 [sing-box 官方 URLTest 文档（外链）↗](https://sing-box.sagernet.org/configuration/outbound/urltest/)。

**常见逻辑错误：** 规则指向 selector，但 selector 内没有有效节点；自动测速组成员标签已被删；把自动测试的“低延迟”误认为目标服务一定可用。遇到这些情况，先在同一网络下手动选中一个成员访问同一目标，再判断是策略组还是节点问题。

## 四、启用 TUN：先建立最小可用状态

TUN 会把更广的系统流量交给客户端处理。启用前，先关闭其他 VPN/代理客户端，确认系统代理、基础规则和一个节点都正常。然后只启用 TUN，保持其余配置不变，验证普通网页、目标网站和本地网络资源三类访问。

TUN 相关选项会随平台不同而不同：Android 图形客户端基于 Android `VpnService`，桌面与命令行客户端的权限和路由能力也不同。官方文档明确列出，Android 图形客户端无法处理某些包含大量路由的地址集，可能出现 `DeadSystemException`；这不是“节点失效”，应减少复杂路由、恢复最小配置，或改在适合的系统环境使用。 [官方 TUN 文档](https://sing-box.sagernet.org/configuration/inbound/tun/)

启用后所有网络异常时，按顺序回退：关闭 TUN → 验证未使用 TUN 时网络正常 → 检查 VPN 权限和设备管理策略 → 再检查是否同时运行其他 VPN。不要一次改 MTU、DNS、路由集和出站标签；这样会失去定位依据。

## 五、日志与错误：按层定位，不要猜

| 现象或日志 | 所在层 | 优先检查 |
| --- | --- | --- |
| `unknown outbound` | 规则到出站 | 规则引用标签、selector/urltest 成员是否存在 |
| `unknown field` / 配置校验失败 | 配置语法 | 内核版本、字段路径、官方迁移说明 |
| `permission denied` / 无法启动 VPN | 系统权限 | 另一 VPN、系统授权、受管理设备策略 |
| `DeadSystemException` | Android TUN 路由负载 | 关闭复杂地址集，恢复最小 TUN 配置 |
| 规则命中正确但连接超时 | 出站或网络 | 固定同一节点、网络和目标，查看 DNS/TLS 错误 |
| 全局代理成功、规则模式失败 | 规则层 | 日志中的规则命中和最终出站 |

需要排查 DNS、校园网认证或缓存时，使用 [网络测速与 DNS 诊断指南](/posts/38-network-speed-dns-diagnostics-guide)。发送日志给支持人员时，只提供时间、版本、错误行与打码后的标签；不要发送完整订阅 URL、令牌或整份配置。

## 六、常见问题（FAQ）

### 新加规则后完全没有命中，是规则语法错了吗？

不一定。先确认访问的是实际写入的域名、规则顺序没有被更通用规则抢先命中，并从日志确认请求是否进入该客户端。再检查规则所指向的出站标签。

### 自动测速组经常切换节点，是否应把间隔设得很短？

不建议。频繁切换会让会话、下载和登录状态难以复现。先固定一个节点验证问题，再按官方 URLTest 行为设置合理测试周期。

### 开启 TUN 后局域网设备或校园认证页不能访问怎么办？

先关闭 TUN，完成认证并确认本地网络正常；再检查路由排除项与当前平台支持范围。不要为临时访问一个页面而把所有流量长期改为全局代理。

### 应该直接编辑服务商订阅下载的 JSON 吗？

不建议。远程更新可能覆盖修改，且难以追踪来源。优先通过客户端支持的覆写、独立本地配置或由服务商提供的规则入口实现，并保留可回退版本。
