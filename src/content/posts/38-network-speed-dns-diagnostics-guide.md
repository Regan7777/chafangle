网络出问题时，最容易犯的错是同时切节点、改 DNS、打开全局模式、重启多个 App。这样即使恢复了，也不知道真正原因是什么。更稳妥的做法是：**一次只改变一个条件，并记录结果。**

先记住四件事：

- **节点延迟**只表示建立连接的快慢，不等于网页、视频或下载一定快。
- **测速结果**反映某一时刻、某一测试点的网络表现，不能代表所有网站。
- **DNS**负责把域名找到对应地址；它不负责账户登录、视频清晰度或服务端拥堵。
- **规则和系统代理**决定请求有没有进入客户端；如果路径根本没进入，换再多 DNS 也不会生效。

不理解“订阅、节点、客户端、规则”之间的关系时，先读 [网络客户端入门指南](/posts/23-fanqiang-basics-airport-vpn-beginners-guide)。本篇只负责诊断：到底该检查网络、客户端、DNS，还是某一个具体网站。

## 一、先给问题分类：你看到的现象属于哪一类

不要先打开测速网站。先用下面的现象对号入座：

| 现象 | 优先怀疑 | 第一步 |
| --- | --- | --- |
| 所有网页和 App 都打不开 | 当前 Wi-Fi、蜂窝数据、校园网认证或系统网络 | 断开客户端，确认基础网络是否可用 |
| 只有一个网站或一个 App 失败 | 规则、DNS、该服务自身状态、登录会话 | 记录完整提示文字，再用浏览器复测 |
| 节点列表有延迟，但网页打不开 | 系统代理/TUN 未接管、规则走错、DNS 或目标站故障 | 在客户端查看当前模式与连接日志 |
| 下载慢、视频缓冲，但网页能开 | 带宽、拥塞、测试点、视频服务自身分发 | 用同一网络在相近时段重复测速 |
| 切换节点后页面内容完全不变 | 应用缓存、长连接、未实际切换、规则仍指向同一出口 | 断开重连后关闭并重新打开目标 App |
| 只有校园网或酒店 Wi-Fi 失败 | 认证页、网络限制或设备注册 | 只完成正常网络认证；若仅客户端功能受限，不再尝试绕过 |

**正常结果：** 你能说清“是所有服务失败，还是只有一个服务失败”；这一步比立刻修改设置更重要。

## 二、固定条件后，完成一次基础网络检查

先在不启用客户端的状态下做一次检查。不要删除订阅，不要改 DNS，不要更换系统设置。

1. 记下当前网络：例如“宿舍 Wi-Fi”“手机蜂窝数据”或“公司网络”。
2. 断开客户端的连接或关闭系统代理，然后打开两个普通网站。
3. 若两个网站都不能打开，问题位于本地网络或认证，暂时不要测节点。
4. 若普通网页可以打开，再开启客户端，选择一个你以前用过的节点。
5. 只访问同一个目标网站一次，记录结果和完整报错文字。
6. 断开后换到另一种网络，例如 Wi-Fi 与蜂窝数据之间切换，再重复第 5 步。

两种网络的结果不同，通常说明问题更接近当前网络环境；两种网络都相同，才有理由继续检查客户端、规则或服务端。Windows 的系统代理、TUN 和端口问题可按 [Clash Verge Rev Windows 教程](/posts/20-clash-verge-rev-beginner-tutorial) 排查；Android 的 VPN 接口、后台限制与导入错误见 [Android 客户端教程](/posts/26-android-v2rayng-surfboard-tutorial)。

## 三、测速怎么测，结果才有参考价值

测速不是“跑一次，数字越大越好”。一次有价值的测速，应当只回答一个问题：**当前网络到这个测试点的响应和传输表现是否异常。**

1. 保持同一网络、同一节点、同一规则模式；先关闭正在下载、云同步和视频播放的设备或应用。
2. 打开 [Speedtest by Ookla（外链）↗](https://www.speedtest.net/) 或 [Cloudflare Speed Test（外链）↗](https://speed.cloudflare.com/)；两者测量方式与测试点不同，结果不必完全一致。
3. 连续测试两到三次，记录下载、上传、延迟，以及平台展示的抖动或丢包信息（若有）。
4. 只在出现明显偏离时再换一个测试点复测；不要反复切换节点和测试点来追逐最高数字。
5. 把结果与“关闭客户端时的同网络结果”比较，而不是只盯一个绝对数值。

**怎么判断：**

- 延迟低、带宽普通：打开网页未必有问题；视频缓冲还应检查具体服务、线路高峰或设备同时下载。
- 延迟忽高忽低、抖动明显：更像 Wi-Fi 干扰、网络拥塞或不稳定路由；先靠近路由器或换网络复测。
- 下载低但上传正常：不能仅据此认定节点有问题；应换测试点、换时段，并排除本地任务。
- 关闭客户端与开启客户端都慢：优先检查本地网络，不要反复更换订阅。
- 只有开启客户端后明显变慢：记录节点、模式和测试时间，再检查规则路径及客户端日志。

测速网站无法证明某个流媒体、游戏或社交平台一定可用。服务的内容分发、账户状态和本地缓存各自独立；相关的服务表现与排查边界，见 [流媒体、社交平台与 Emby 指南](/posts/27-chatgpt-netflix-streaming-ip-unlock-guide)。

## 四、DNS 到底检查什么，不检查什么

DNS 类似通讯录：应用拿到域名后，先问 DNS“这个名称对应哪个地址”。DNS 错误可能导致域名无法解析、解析到不符合预期的结果或等待很久；但它**不能**修复订阅失效、账户限制、客户端未授权或服务端拥堵。

先用 [Cloudflare 连接与 DNS 检查（外链）↗](https://1.1.1.1/help) 查看浏览器当前网络是否按预期使用其解析服务。该页面只是诊断工具，不要求每个人都改用同一 DNS。Cloudflare 的官方说明也建议：解析异常时，应与另一解析器结果对照，而不是仅凭一次网页检测下结论。

按这个顺序检查：

1. **只一个域名失败**：记录浏览器错误和域名；用另一网络复测同一域名。
2. **多个不相关域名都失败**：先关闭客户端，检查基础网络和校园网认证。
3. **确认是 DNS 现象后**：查看客户端有没有自定义 DNS、覆写规则或 TUN/DNS 劫持设置；一次只改一项并保留原值。
4. **改后重新连接**：关闭并重新打开浏览器或 App，再测试相同目标；旧进程可能保留缓存或长连接。
5. **仍无结果时**：恢复到先前可用设置。若关闭客户端时普通网页也不能访问，只向网络服务支持反馈“无法完成认证或基础访问”；不要提交订阅链接、配置或要求其排查客户端行为。

如果你正在使用 sing-box，自定义 DNS、规则与出站会相互影响，先做基础导入验证，再看 [sing-box 基础教程](/posts/22-sing-box-next-gen-proxy-tutorial)；需要配置级的 DNS、出站与规则判断时，继续读 [sing-box 自定义规则、出站与 TUN 指南](/posts/41-sing-box-custom-rules-outbounds-tun-guide)。

## 五、校园网、酒店 Wi-Fi：认证页为什么不出现

校园网、酒店和办公网络常要求先打开认证页；客户端过早接管流量时，认证请求可能走错路径，看起来就像“网络全坏了”。

正确顺序是：

1. 先关闭客户端连接与系统代理。
2. 忘记并重新连接 Wi-Fi；必要时在系统网络设置中重新获取地址。
3. 打开浏览器访问一个普通的 HTTP 页面，或直接使用网络提供方的认证入口；完成账号、短信或设备确认。
4. 确认在关闭客户端状态下能正常打开普通网页。
5. 若需要判断故障是否只出现在当前 Wi-Fi，可断开校园 Wi-Fi，临时使用自己的蜂窝数据，或开启自己的手机热点并让自有设备连接；随后只复测同一个普通网页。若蜂窝数据或个人热点正常、而校园 Wi-Fi 仍异常，说明现象与当前 Wi-Fi 环境有关。
6. 若一开启客户端认证页又被带回、网络中断，立即关掉客户端；不要为了“强行连通”反复更改 DNS、模式和节点。

**正常结果：** 认证在关闭客户端时完成，普通网页可访问；热点或蜂窝网络的对照可帮助定位网络环境。

## 六、切换节点后，为什么结果没有变化

“已经切换节点，结果却没变”不一定代表切换失败。常见原因包括：浏览器或 App 的长连接没有断开、DNS 缓存仍在、客户端规则将该网站导向固定路径，或客户端界面显示已选中但实际连接尚未重建。

请只做下面四步：

1. 在客户端确认当前选择的节点或策略组名称，等待状态显示已连接。
2. 断开一次，再连接一次；不要连续点选多个节点。
3. 完全关闭目标 App 或浏览器标签页并重新打开，再访问同一页面。
4. 若仍不变，查看客户端连接日志里该域名命中了哪条规则；随后对照 [直连、规则与全局代理的区别](/posts/39-direct-rule-global-proxy-modes-guide)，确认当前模式是否符合你的测试目的。

不要把“全局模式”当作所有问题的固定答案。它只适合在你需要确认“规则是否导致路径不同”时做一次短暂对照；确认后应回到日常需要的规则模式。

## 七、常见问题（FAQ）

### 测速显示很快，但网页仍然打不开，先看什么？

先看是否只有一个网站打不开。若只有一个，测速不能证明该网站的解析、规则、登录状态或服务端正常。记录错误文字，换网络复测同一网站，再检查客户端日志中的规则命中。

### 浏览器提示 `DNS_PROBE_FINISHED_NXDOMAIN` 或 `ERR_NAME_NOT_RESOLVED`，就是 DNS 被污染吗？

不一定。这类提示只说明当时没有得到可用的域名解析结果。先核对域名拼写、网络认证、客户端 DNS 设置和另一网络的复测结果；不要直接把它等同于某一种原因。

### 日志出现 `SERVFAIL`、`timeout` 或“解析超时”，该怎样做？

`SERVFAIL` 表示解析过程未能完成，`timeout` 表示在等待响应时超时。它们可能来自当前网络、解析器、目标域名服务或客户端 DNS 配置。先保持其他设置不变，换一次网络或对照解析器；若只在特定网络发生，保留发生时间和网络类型后反馈。

### 节点延迟显示正常，为什么打开 App 还是“无网络连接”？

延迟测试通常只验证到某个地址的连接，不代表系统代理、VPN 权限、规则或该 App 的具体请求均正常。分别检查客户端是否真正已连接、系统 VPN/代理是否启用，以及该 App 是否需要重启。iOS 的 VPN 授权与规则入口见 [Clash Mi iOS 教程](/posts/40-clash-mi-ios-beginner-tutorial) 和 [Shadowrocket iOS 教程](/posts/21-shadowrocket-ios-beginner-tutorial)。

### 切换 Wi-Fi 后突然全部失效，需要先改 DNS 吗？

不用。先完成新网络的认证并确认关闭客户端时能正常访问网页。很多校园网和酒店网络在首次连接时要求认证或设备登记；没有完成认证前，改 DNS 往往只会增加变量。若该网络不允许相关客户端功能，到此停止，不提供规避方法。

### DNS 检测页显示的不是我设置的解析器，是不是泄漏？

先确认你测试的设备、当前网络与客户端状态一致。系统、浏览器、客户端和路由器可能各自设置 DNS；检测页只反映测试当时的查询路径。记录结果后逐层检查，不要在不了解作用的情况下同时开启多种 DNS 覆写。
